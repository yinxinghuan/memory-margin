# 用户新房间生成全流程计时

## 房间假设

用户要求一个具有独立功能的新房间。本次选择“记忆真伪鉴定室”：左右设备分别扫描原样和对照记忆，中央设备比较残响，右下设备封存证物。

遵循“少量复用通用件、房间功能由新素材表达”：

- 复用：主角、北/侧/前景墙、门洞、摇杆和 RPG-JS 行走层。
- 新生成：专用地面、残响扫描器、双样本比较器、封存缓冲器。
- 同一新扫描器放置两台，分别承担原样和对照工位；没有用旧终端改名冒充。

入口：`?generated_room=1`。

## 渐进进入复验

复盘后增加 `?generated_room=1&room_phase=shell`：只加载复用墙体、主角、程序网格和四个语义体积，不消费本房间新生成的地面与设备图片。四个体积直接使用最终 `auditPlacements` 的同一组坐标和 obstacle，RPG-JS 行走、点击寻路、出生点、出口和碰撞已经生效；高保真素材准入后在相同槽位原位替换。地图持续显示 `role=status` 的“世界正在加载”，同时说明玩家可以先探索；没有真实任务统计时不显示百分比。

`_qa/capture-generated-room-shell.mjs` 单独测量已有骨架从页面请求到 RPG canvas 可操作的启动时间，写入 `_qa/generated-room-shell-results.json`。三次复验中，390×844 为 **539–705 ms**，320×568 为 **365–375 ms**，均无 page error。这个数只证明骨架已存在时的运行时进入速度；本轮最初没有在媒体请求前记录“需求到骨架完成”的制作墙钟，所以不追溯臆造该数字。下一次新房间基准必须同时记录：`brief → shell interactive` 与 `brief → high-fidelity accepted`。

截图证据：`_qa/platform-layout-generated-audit-shell-390x844.png`、`_qa/platform-layout-generated-audit-shell-320x568.png`。

## 真实媒体任务恢复复验

`?generated_room=1&room_phase=live&reset_room_media=1` 会清空该房间的作用域状态，再用四个实际平台任务的 `task_id + request_id` 恢复素材。房间先显示与完成态同槽位、同 footprint 的骨架；每个任务确认成功后，才用对应的本地准入素材原位替换。刷新时已接受槽位从作用域存储立即恢复，不重新提交或重复查询。结构化失败只留下该槽位占位，其余任务继续完成；玩家只看到“有些细节还在路上”。

本地浏览器不能直接从 `127.0.0.1` 调平台接口，实测得到 `ORIGIN_NOT_ALLOWED`。开发与预览服务器因此提供 `/__alteru_media__` 窄范围同源代理；正式平台域名继续直连平台媒体服务。该错误与接口细节没有进入玩家文案。

`_qa/capture-generated-room-live.mjs` 真实访问四个已完成的平台任务。2026-09-19 的结果写入 `_qa/generated-room-live-results.json`：

| 视口 | 骨架可操作 | 首次观察已替换 | 四项完成 | 刷新恢复完整房间 |
|---|---:|---:|---:|---:|
| 390×844 | 510 ms | 1 / 4 | 1575 ms | 179 ms |
| 320×568 | 369 ms | 0 / 4 | 644 ms | 183 ms |

两种尺寸均无 page error、无失败槽位，最后是四件正式素材、零占位；截图为 `_qa/platform-layout-generated-audit-live-390x844.png` 与 `_qa/platform-layout-generated-audit-live-320x568.png`。`_qa/progressive-room-media.test.ts` 另用可控任务读器验证逐项乱序回填、刷新不重复读取已接受槽位，以及单件终止失败不阻塞其他素材。

## 结论边界

这个复杂度的单房间本次实测约十分钟。它包含一次平台失败和一轮设备视觉返工，因此比全部首轮通过的情况更接近当前真实生产条件。该数字不包含剧情互动、人物对白、房间状态变化或正式章节接入；增加这些内容需要另行计时。

素材生成和场景装配都不可省略。平台调用速度很快，但视觉筛选与可玩房间验证占据大部分时间。复用墙、门、人物和输入系统能显著缩短房间工程时间；房间功能仍由四类新视觉素材表达。
